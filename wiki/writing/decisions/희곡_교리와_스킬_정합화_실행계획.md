# 희곡 교리와 스킬 정합화 Implementation Plan

> **For Hermes:** 단계마다 한 파일 또는 한 스킬 묶음만 수정하고, `재독 → 오래된 규칙 검색 → 단계별 검증`을 통과한 뒤 다음 작업으로 이동한다. 서로 다른 작업을 병렬 수정하지 않는다.

**Goal:** `희곡_길이별_설계_원리.md`를 복수 형식 생성의 단일 교리원으로 만들고, 관련 교리·운영 문서와 스킬 3종을 중복 없는 실행 체계로 정합화한다.

**Architecture:** 상위 미학은 작품 고유성 보호, 판정 루브릭은 가능성 진단, 길이별 설계 원리는 형식 후보 생성·비교, 집필 파이프라인은 선택 형식 실행을 담당한다. `play-seed-harvesting`, `playwriting-dramaturgy`, `bookclub-wiki-v2`는 각각 채집, 극작, 위키 운영만 담당하는 얇은 어댑터로 유지한다.

**Tech Stack:** Markdown/YAML frontmatter, Obsidian wikilinks, Hermes `read_file`·`patch`·`write_file`·`skill_manage`·`skill_view`, Python `zipfile` 기반 백업·검증, Git diff/status 읽기 전용.

**Commit policy:** 현재 vault의 다른 변경과 Git 인증 맥락을 보존하기 위해 이 계획에서는 커밋·푸시 단계를 의도적으로 생략한다.

## 공통 실행 계약

각 작업은 다음 여섯 단계를 반복한다.

1. 수정 직전 대상 파일을 다시 읽는다.
2. 한 파일 또는 한 스킬 묶음만 수정한다.
3. 수정본을 처음부터 끝까지 재독한다.
4. 그 단계에서 제거하기로 한 오래된 강제 문구를 검색한다.
5. frontmatter·wikilink·역할 경계를 검증한다.
6. `log.md`에 변경·검증·남은 범위를 한 항목으로 기록한다.

다음은 완료 증거가 아니다.

- 파일을 저장했다는 사실
- 검색 결과가 적어 보인다는 인상
- 전체 verifier의 기존 오류와 이번 변경을 구분하지 않은 수치
- 스킬 본문만 고치고 연결 참조 파일을 확인하지 않은 상태

### Task 3: 글감 판정 루브릭을 가능성 진단기로 재설계

Move it from universal prerequisite to `최소형 시험`. Keep it as a useful Hirata-derived lens.

**Step 2: Split common seed qualities from form-specific affordances**

- human amplitude
- concept surplus
- stageable physical action
- information or authority difference
- repetition with changed function/cost

Form affordances:

- continuous real-time
- vertical repetition
- multiple simultaneous flows

- protected core
- strongest current form affordance
